# Codex consumer integration

The V3 owner accepts the bounded deterministic consumer scope. This is a new
provider route, not a replacement for accepted Claude evidence. Runtime admission
belongs to Experiment; acquisition and immutable decisions belong to Client;
qualification and independent archive validation belong to Journal.

## Design before implementation

Use the existing one-shot async Client and original StartedExecution through
Experiment. Retain the original response before qualification, the actual
termination receipt, original decision and capture, including failure paths.
Select the explicit Codex terminal profile and reject foreign execution or
archive identities. Never reconstruct a successful response or decision.

The pinned PetClinic before-tree, simple prompt, baseline/final independent
measurement, edit-surface/build/coverage Jury, detached reader and nine ACT
outputs remain required. The existing Claude route and its immutable accepted
archive stay unchanged. A local executable fixture exercises wiring only.

Codex native launch remains closed. The existing product policy permits writes
only under src/test and exactly the foreground Maven build command. Workspace
write sandbox alone does not enforce those requirements. The final proposal must
state actual writable roots, operation limits, process cleanup and wall-time
controls; unknown cost and unsupported token/internal-turn ceilings remain explicit.
No synthetic policy observation qualifies native write/edit behavior.

## Verification boundary

Use an isolated Maven cache with exact producer hashes. Run the complete offline

## Implemented deterministic route

`NativeCoverageApp` accepts the existing Claude options unchanged. The explicit
Codex fixture variant replaces `--claude-executable` with `--codex-executable`
and `--codex-fixture-mode success|failed|wrong`. It verifies the child and native
template against the packaged resource hashes. The separate fixture ledger has
kind `v3-codex-fixture-only/1`; it consumes no historical native allowance.
The pipeline manifest selects `provider=CODEX` and `mode=SYNTHETIC_FIXTURE`.
Both the launcher and the public native-open entry point reject Codex native work.

The composition uses Client's actual Codex provider, async execution and sealed
acquisition. The original public Journal recorder produces the original decision
bytes. A separate complete receiver envelope retains those bytes; the recorder
returns that receiver's actual binding ID to Client. Experiment verifies that
binding with the original execution and response. Capture paths are retained as
hash-checked references returned by Client, never guessed from execution IDs.
Archive failure records its original exception without replacing the Client result.

## Native proposal and controls

read-only probe's Codex 0.166.0 selection. Its explicit model is gpt-6-luna/high;

Read-only cannot perform the task. Workspace-write does not limit writes to

The current test-only policy gate therefore remains NOT_READY. Protected-file
comparison remains a separate post-run observation.

The smallest reviewable options preserve the product's acceptance requirements:

1. Keep native work held while a separately scoped provider policy capability
   supplies and tests synchronous path/operation denial for the existing policy.
2. Separately design an isolated execution boundary with a test-only write mount
   and an operation broker that exposes the exact trusted build command. Filesystem

   need their own deterministic and native proof before activation.

Neither option is implemented or authorized by this deterministic return. A Client
change is not presumed: the selected route limitation must first be assigned to
its actual owner. Proposed execution remains 900 seconds plus 15 seconds cleanup,
inside the shared 1,800-second pipeline with independent measurement/reader/ACT

All ten acceptance gates remain: launch integrity, Client cleanup, native sources,
required policy, protected inputs, archive reader, Workflow result, full Jury,

## Candidate policy disposition

The V3 owner accepts deterministic preparation of a workspace-write candidate.
It is explicitly different from the prior preventive hook: the proposed workspace-write sandbox requests a workspace boundary; its effective
writable roots still need qualification. A complete after-inventory and command evidence
determine whether the result is acceptable. Test-only intent is an instruction,
not preventive write enforcement. No native activation follows this disposition.

The candidate verifier will reject protected new/changed/deleted paths, symlinks,
file-type or mode changes and missing/disallowed command evidence. Generated
`target` content is retained as observed build output and excluded from the patch.
Only the validated test patch is applied to a fresh pinned verification copy.
The harness performs the same bounded exact foreground Maven command there and
rechecks protected files. Submitted test code is executable; its process and
filesystem effects need the selected disposable isolation, not a read-only claim.

The first proposal remains one fresh Codex execution; no planner/edit/reviewer
split. Writable cache/build paths, evidence completeness, actual command policy
and timeout/cleanup limits must be named in the frozen proposal. Unsupported
transient-write/escaped-process/dollar/token/internal-turn guarantees stay explicit.

The candidate verifier is `scripts/verify_codex_candidate.py`. Its local tests
exercise valid changed/new tests, protected tracked edits, untracked protected
files, symlinks (including under generated output), mode changes, excluded target
output, incomplete/disallowed operations and changed/nonfresh verification copies.
The patch transfer rechecks subject hashes before copying and verifies the result.
The command-observation input must come from a complete independently qualified
source population in a future native run; its structural fixture checks are not
that producer proof. Its output always says `nativeAcceptance=false`.

The candidate command vocabulary permits the exact foreground Maven command and
small read forms (`pwd`, `rg --files [relative-path]`, `cat -- relative-path...`),
plus observed test-only `apply_patch` paths. Compound/redirection/expansion,
background actions, unknown tools and missing completion/source occurrence are
rejected. This is an explicit proposed policy delta from Claude's preventive

For deterministic full-task wiring, the packaged child can apply an explicit six

## Source-bound command subset and remaining launch holds

`project_codex_commands.py` verifies every original capture digest/extent/EOF,
execution and native identity, the single turn, context and explicit working
directory, all native calls/outputs and all sequential stream command starts/
completions. It supports only the exact observed literal `exec` wrapper around
one `tools.exec_command`, with known scalar options and output printing. It never
evaluates JavaScript. Unknown code, tools, unmatched populations, incomplete
operations, parallel activity and foreign directories fail closed. The accepted
read/failure/recovery capture replays offline as three original operations with
exit codes 0/1/0. This is source projection proof for that observed read subset.

The candidate validator recomputes any source-backed projection before using it.
Structural fixture inputs remain labeled STRUCTURAL_ONLY. Edited results require
nonempty operation evidence and observed patch paths covering every changed test
file. Unsupported direct/code-mode `apply_patch` shapes are currently rejected by
the source projector: the write-enabled candidate is therefore **NOT_READY**.
The public native entry point also remains closed. The smallest remaining work
is an owning, fail-closed edit-operation projection plus the reviewed candidate
native entry/activation gate; new live edit evidence is still a separate launch.

Proposed compiler feedback is at most one observed exact foreground Maven build
inside the one subject session. The configured subject deadline is 900 seconds;
there is no demonstrated independent per-command kill bound. The supported
literal call may request a 30-second tool wait, which is a yield threshold, not
an execution cap. Background/wait-session tool shapes remain unsupported and
cause acceptance refusal. The independent harness build has its own 600-second
process timeout and 15-second kill grace inside the remaining shared pipeline
budget. Its timeout is separate from source-session feedback. Running submitted
tests executes code as the harness user; a disposable directory is not an OS
containment guarantee. Any stronger filesystem/network/process isolation needs
its own selected implementation and verification before it can be claimed.
